# Verification scope and evidence

The improvement is checked as a local personal CRUD application. Tests use fictional records, temporary SQLite databases, loopback HTTP, and controlled Chromium. They do not open the existing personal profile or browser session, submit applications, invoke paid models, or follow job links to external sites.

`python scripts/verify.py` parses project Python modules and runs 43 tests. The report is `.verification/model.json`. Store tests exercise real transactions, audit-trigger failures, and competing writers. HTTP tests make actual local requests. Import tests validate repeat, duplicate, malformed, rollback, and deletion behavior. Profile and CLI tests check bounded input, unknown answers, relative paths, backups, and cleanup. The automation lifecycle cases use fakes and therefore do not establish live career-site compatibility.

`python scripts/verify_browser.py` runs eight Chromium scenarios: CRUD and token lifetime; two-tab conflict with draft export; real database failure retaining the draft; literal HTML rendering and search; confirmed locking; last-page deletion; successful save followed by failed list refresh; and desktop/narrow layout. All eight passed in the implementation review. It writes `.verification/browser.json` and two images. [Desktop](images/desktop.png) and [narrow](images/narrow.png) screenshots were visually reviewed, with no horizontal overflow at the tested 1440- and 390-pixel widths. This is not a complete accessibility audit.

The checked environment used Python 3.13, PyYAML 6.0.3, pydantic 2.13.4, and Python Playwright 1.59.0. The controlled executable was the task's existing Chromium 148 installation. Development requirements pin the tested Python packages. A normal Playwright browser installation may use its matching revision; rerun the suite there. Node 22.16.0 checks browser JavaScript syntax and is not needed to run the tracker itself.

Limits remain explicit. The loopback server has one per-process access token, no accounts, owner isolation, distributed limits, or hosting configuration. New POST requests lack durable idempotency receipts, so uncertain retries require inspection. Audits retain minimal metadata rather than every old value. Search follows SQLite's default text comparison. Import is bounded and explicit; the UI has no import wizard or automatic draft merge.

The original provider adapters and their configured model defaults were not verified against live services. The offline planner's unknown-answer and consent behavior has focused coverage. Backup checks use SQLite's backup API, but power-loss behavior, deployment, full assistive-technology coverage, and hostile multiuser operation were not certified. Update this file with observed results when extending the project, and keep proposed practice features clearly separate from implemented behavior.

To reproduce safely, install the development requirements in a virtual environment, install Chromium, run both verification scripts, and inspect their JSON reports and images. Temporary test resources are closed and cleaned after each case; your real application history is outside those fixtures.
